## 1. 本次必须完成什么

本次实施范围包括明确操作记录、权威数据接纳、身份绑定、派生展示、撤销/重做、冲突处理、保存调度与回执，以及编辑输入和运行中异步任务的归属。不能只把新内核放进目录，或只替换编辑入口。

完成后的数据流必须是：

```text
旧 UI / 旧 cell-types / 宿主命令
                 ↓
现有 Controller workflow：处理交互、准备完整命令
                 ↓
现有 Runtime：原子发布核心状态与界面快照
                 ↓
权威事实 + 不可变操作记录 + 提交证据 + 历史控制记录
                 ↓
派生 rows / dirty / conflicts / save plan / undo capability

网络与任务执行 → 带身份的结果事件 → 同一个 Runtime
```

必须满足以下不变量：

1. 展示行、dirty 和 conflicts 只供读取，不能被用于重建已经存在的用户意图。
2. 刷新只增加或更新可证明有效的权威事实，不删除尚未结算的本地操作。
3. 回执只结算被该次提交覆盖的操作；保存期间追加的编辑不能被一并清除。
4. 保存结果未知、已写入但缺回执、已确认完成是不同状态；未知结果不能被当作未执行而重新发送新请求。
5. 撤销/重做作用于具体操作贡献；已经保存的修改通过补偿操作撤销，不恢复整份旧 rows。
6. 编辑原文、目标、组合输入和异步任务归属不能由 DOM 生命周期或当前选区推断。
7. 一次 Runtime 发布包含一致的核心状态、展示、查询结果、会话和能力；订阅者看不到中间版本。
8. 一张表格的数据域只有一套可写状态和一套有效历史。

## 4. 状态所有权和同步边界

### 4.1 一个 Runtime，明确的状态分区

继续由 `GridControllerRuntime` 同时提交公开 snapshot 和内部状态。建议的逻辑分区如下，具体类型名在实施时确定：

| 状态 | 唯一写入者 | 读取方式 |
| --- | --- | --- |
| authority、实体绑定、journal、提交账本、历史决策 | 数据 reducer，经 Runtime 发布 | 数据投影和保存计划 |
| 编辑/批量/过滤会话、原文、composition、输入版本 | 会话转换，经同一 Runtime 发布 | 原编辑器 props 与命令准备 |
| query、selection、layout、菜单、反馈 | 现有交互/视图转换，经 Runtime 发布 | 原 React selectors |
| 任务目标、会话版本、取消与结果状态 | 任务所有权转换，经 Runtime 发布 | 图片控件及异步结果处理 |
| AbortController、timer、Promise、文件句柄 | 现有 effect runner 或资源容器 | 只通过具名结果事件改变语义状态 |

原 `snapshot.draft` 在迁移期间可以作为只读兼容投影。禁止对它继续运行旧 draft reducer，禁止把它的历史数组交给旧 `restoreHistory()`。

旧会话与备份 session 不能各保留一份可写 draft。首轮复用旧会话入口和编辑器契约，补足稳定 sessionId/inputVersion/目标依赖；需要编码后交给内核的材料使用明确的记录和引用，不镜像同步两份会话。

### 4.2 同步接纳与远端保存分开

- `dispatch()` / `applyTransaction()` 保留同步语义：返回时本地操作已经接纳或拒绝。
- 单格编辑提交成功后才能移动选区；校验失败保留输入与焦点。继续复用 `prepareTransition()` 的产品行为。
- Runtime 先原子发布状态，再执行网络、任务和 timer；完成事件携带 scope、操作和目标身份重新入队。
- 本地接纳不表示服务器已保存，也不表示已经写入 IndexedDB。本轮不承诺浏览器崩溃后的输入恢复。
- 不为每次键入、选区变化或菜单操作引入异步存储屏障。
- 如果后续引入“接纳前必须持久化”，需为该模式明确设计异步接纳接口及待确认反馈；不能沿用同步 accepted 的含义。

## 5. 必须先解决的连接契约

### 5.1 Row、字段与自定义 setter

保留旧 `getValue/setValue`、registry 和编辑器。备份的 DocumentCodec 用于声明完整行的无损编码；普通编码对象可提供默认 codec，Date、自定义类、非有限值等必须显式编码，不能用 JSON.stringify 静默改变数据。

字段绑定不由 columnKey 猜测。字段路径、别名列和复合字段在配置编译阶段明确映射；多个列写同一存储字段共享其身份。

一次编辑的准备过程：

1. 固定目标、原始上下文、输入与权限。
2. 调用原 cell behavior 解析和校验输入。
3. 在隔离的候选行上执行 setter，得到确定的完整写集合；setter 不进入 journal。
4. 验证所有目标、写入域、只读限制和完整行约束。
5. 将完整计划作为一次 action 接纳；任一步失败，不发布部分修改。

显式声明的 `planEdit/read` 可产生字段级依赖。只有任意 setter 的旧配置采用保守整行比较，捕获完整行依赖；允许更多冲突，不能漏掉 setter 读取的其他字段。整行候选的差异只用于编译这一次明确命令，不用于刷新后反推历史意图。

输入编码与行编码分别处理。原 Editor/BulkEditor 的 draft 类型不改成统一字符串：标准 draft 使用相应编码，自定义结构需要明确的输入 codec；文件由资源容器保留并通过引用进入记录。任何编码失败都在接纳前报告并保留原输入，不能丢弃不支持的部分后提交。

### 5.2 实体身份

内部 EntityId 与服务端主键分开。临时行 ID 在服务器分配主键后继续稳定，更新绑定；选择、编辑、历史、上传任务使用同一身份映射。服务端主键复用必须有 incarnation 或明确的 epoch 内不复用保证。

保留对宿主字符串/数字 RowKey 的支持。映射时保留类型，禁止把数字 1 与字符串 '1' 混成一个键；不能根据一份最新 rows 临时重建全部映射。

### 5.3 数据源与保存证据

升级旧 GridDataSource 的数据协议，保留 UI 入口。优先复用备份协议已经表达的能力：

- scope/epoch、可验证的有序或因果 authority 版本；
- 固定 operationId 和请求身份，版本前置条件与作用域写入隔离；
- 精确对应提交项的回执、创建绑定与规范化后的结果；
- 已确认写入但回执/权威读取失败的独立状态；
- 操作查询与幂等保证，以及其有效保留期限。

不能用接收顺序生成“服务器版本”，不能用 HTTP 200 或值相等补造精确回执。旧 opaque version + afterOperationId 能证明的关系可保留；不能证明的结果保持待确认。新协议必须由 demo source 和真实宿主适配器提供，必要时接受明确的 API breaking change。

是否允许来源适配取决于它实际提供的证据；不能声明一套强能力，内部却通过旧行数组缓存模拟。无法满足的能力在配置/操作入口明确报告，保留已接纳工作。

### 5.4 原问题对应的状态转换要求

以下是实现必须表达的结果，不是本阶段新增测试的任务清单：

| 情境 | 必须保留的事实和结果 |
| --- | --- |
| 保存 A 时继续编辑成 B，随后 A 的回执到达 | 只结算 A；B 仍是未保存操作，显示 B |
| 已接纳较新 authority，随后收到旧读取或旧保存回执 | 可记录旧提交的精确证据，不把 authority 或展示退回旧版本 |
| A 行删除发生冲突，B 行可以保存 | 保存 B 不清除 A 的删除意图；冲突展示的 A 不被误认成新建行 |
| setter 已经生成明确写集合，刷新后上下文变化 | 回放写集合，按捕获依赖判断冲突；不重新执行 setter 或删除原目标 |
| 保存请求发送后超时，用户执行撤销 | 原请求内容及未知结果继续保留；撤销等待明确证据决定抑制还是补偿 |
| 服务器分配了新主键，上传或编辑稍后完成 | 用稳定实体/会话身份确认归属，不按当前行号或最新主键猜测目标 |
| 已确认写入，但最新权威读取失败 | 显示等待同步；不重复写入，不清理尚未覆盖的修改 |
| 一批目标中存在拒绝，或权限/字段依赖发生变化 | 按 action 的原子边界拒绝，不丢掉整批输入，也不发布部分本地结果 |

本地 action 的原子性与跨 action 的可保存子集分别定义。一个有冲突的原子 action 不能被拆成部分提交；独立 action 是否可先保存由明确的依赖和保存策略决定。

## 8. 集中修改阶段的工作纪律

- 修改阶段不新增单元测试、浏览器 spec、mutation case 或覆盖率门槛；不批量迁入备份测试。
- 不每修一个交互就运行全量。仅在需要时运行生产代码编译、必要构建和依赖边界检查；它们不是功能完成证据。
- 现有测试保留。内核内部接口变化造成的测试迁移在后续集中处理；不能为了暂时全绿保留旧生产写入者，也不能删断言、跳过失败或把测试配置改弱。
- 临时以不含测试的生产构建检查实现；若 demo 类型检查被旧测试引用阻塞，明确记录原因，不扩成当前的测试改造任务。
- 功能接齐后启动原四个 demo，按完整用户流程集中检查和修正：输入、应用、保存、刷新、继续编辑、撤销，以及失败后的输入保留。
- 用户确认功能前不扩写测试。确认之后再决定哪些真实故障需要最小回归覆盖，并统一执行必要检查。
- M1–M5 期间不 bump、不发版、不更新线上 Pages；代码实现、功能验收和发布准备分别报告。

## 9. 本轮后置范围与明确限制

IndexedDB 的接纳前持久化、checkpoint/跨刷新恢复、持久任务查询、跨进程 lease/fence 和完整关闭恢复 UI 不列入 M1–M5。它们不能被删除后还宣称已经具备，也不能成为本轮恢复产品功能的前置条件。

本轮必须实现运行期间的数据一致性、明确的输入/任务归属和保存结果待确认状态。后续若继续要求进程退出或刷新后恢复，需要单独接入存储屏障及协议；不能把“同步接纳后异步写一个快照”宣传为崩溃安全。

不新增虚拟化、新编辑器体系、通用跨表事务平台或外观设计项目。当前旧版没有的能力不作为本次完成门槛。
