# 测试审计：2026-09-12

本轮目标是删除可证明重复或仅服务迁移的测试，并检查测试预期是否来自业务契约。不是按比例删测试，也不把高覆盖率当成正确性证明。生产代码未修改。

## 删除与保留的依据

- `redo-model.test.ts` 删除 16 个没有远端事件却改变远端值的重复组合，以及 2 个原请求被拒绝、规范化函数不会执行却改变规范化值的重复组合。保留远端变化发生时机、是否保存原操作/撤销、是否提前 redo、实际成功规范化值等有效差异。
- `shared-state-bases.test.ts` 删除 48 个迁移期对照：16 个历史/保存 seed 和 32 个结构组合。它们重复已有独立业务模型场景，并额外要求新解析器与旧解析器一致；旧解析器共用生产文档操作和控制解析，不能独立证明业务正确。删除其两个专用辅助文件及无人调用的观察回调。
- 保留该文件的直接语义回归：精确回执与较新 authority 分离、旧状态缓存隔离、semantic-read/policy-guard 不被改写、隐藏字段与后继意图保留。
- 保留独立保存、历史、结构、任务模型及其原种子数量。未获得每个种子的独特覆盖证据，不能据“看起来类似”删除。
- 保留底层数组/共享前缀算法对照：这是局部算法等价性证据，不称为独立业务规格。也保留已有性能退化回归；内部操作次数不等价于整体运行时间。

## 测试准确性修复

`redo-model.test.ts` 两处和 `tests/kernel/save-trace.ts` 一处原来捕获任意 `freeze` 异常，把它们当成没有内容可保存或无效生成序列。现在只接受明确的 `Nothing can be saved`；其他错误继续抛出。未决请求不能被静默当成空保存。

扩展已有测试工具回归，向参考模型注入 `TypeError`：修复前测试失败，因为回放返回 `invalid` 而没有暴露异常；修复后要求原异常透传，同时确认真正的空保存仍为 `invalid`。没有为增加数量另建一组种子。

## 语义核验范围

重点对照设计契约审阅了保存/回执/旧读、覆盖精确、unknown undo、redo 计算输入以及输入守恒的模型和直接回归。保留的断言分别检查可见值、冲突成员、真实 fixture 服务器内容与写次数、原始输入、冻结请求，而非只比较内部状态标签。

例如，`persistence.test.ts` 将 exact canonical=1.5、后继输入=2、较新 authority=3 分开断言；重复旧读不能覆盖 authority 或删除后继输入。`reference-model.test.ts` 的未应用 undo 分支保留远端新值，不向服务器补写旧值。它们没有把原“保存后回退旧数据”定义为应有行为。

本轮未发现并确认一条业务断言要求上述已知错误发生；发现并修复的是测试工具掩盖异常的缺陷。这不构成对全部单元及浏览器测试的逐断言无错证明。浏览器测试只扫描了跳过、快照和异常捕获模式，本轮未重跑，也未逐条完成 UI 语义审计。

## 后续：有业务价值的未覆盖分支

优先补齐保存协议的矛盾证据处理，在 `persistence.test.ts` 增加 4 个用例：先应用后拒绝、先拒绝后应用、重复/改变的拒绝证明、重复/冲突的提交凭据与后续拒绝。预期来自不可改写已确认事实、输入守恒及不可重复提交的契约；明确检查原事实、后继输入、冻结请求、可见值、协议争议和副作用。不是仅断言分支返回值。

首轮定向测试中一处错误消息预期不准确：未决请求先被未决状态校验阻止，而不是先报协议争议。保留“不允许新保存”的业务要求，修正该消息断言，并补检查重试不产生 submit。未因此修改生产代码。

全量 1203 条通过，类型/边界/lint 通过。新增覆盖 10 个分支，`persistence.ts` 分支覆盖从 114/139（82.01%）到 124/139（89.20%），整体 4734/6938（68.23%）。本次追加测试未重跑变异或浏览器套件；上节变异结果对应删减后的 1199 条基线。

下一批候选需先构造真实边界事件，而非伪造不可达内部状态：

- 同一 authority 版本返回不同内容，以及保存版本的顺序与精确回执不一致：拒绝不一致读，不能回退数据或错误结算顺序。
- durable 存储准备或 checkpoint 验证期间租约失效：旧实例不能发布状态、执行后续写入或清除输入。
- 任务保存的 replace/delete/order 动作在重新接纳时遇到实体/顺序变化：原比较仍有效才接纳，否则保留结果供审查，不重新执行业务回调。

未优先补数值溢出、类型系统已限制的非法枚举、内部自洽检查等仅为提高数字的分支。React 和 IndexedDB 的低 Vitest 覆盖仍需结合浏览器测试判断。

## 后续第二批：租约、读取一致性和结构任务

增加 11 个有业务差异的场景，生产代码未变：

- `durable-commit.test.ts` 两种资源准备结果（成功/失败）均在准备期间由新 session 接管真实 fixture 租约。验证旧 barrier 被 fenced、没有额外存储提交、已发布根及状态不变、原文仍在旧 ingress 队列，新实例可恢复最后已提交状态。使用受控异步资源导出暂停准备阶段；不把保留在内存中的新输入说成已经持久化。
- `gateway.test.ts` 同一版本的不同文档被拒绝，一致的后续读取仍可成功；本地编辑和隐藏字段不被错误读覆盖，无服务器写入。
- `persistence.test.ts` 直接 authority 入口也拒绝同版本不同内容，并验证下一真实版本更新隐藏字段时，本地编辑和待保存内容仍正确。
- `order.test.ts` 真实 fixture 保存顺序后，提交版本的错误顺序读使回执受阻，不提前结算、不重发；一致读到达后仅结算原顺序意图，保存期间的新字段编辑及原文保留。
- `task.test.ts` replace/delete/order 各有比较未变与比较变化两种结果。未变则消费一次并产生明确结果；变化则保留任务结果和输入，显式再次消费仍拒绝，无业务回调重跑或 submit。排序的变化通过真实新建行事件发生，而非手工损坏 journal。

## 后续第三批：补齐非 IndexedDB 恢复链路

按用户限定，不增加 IndexedDB 或浏览器测试。生产代码未修改，新增 7 个场景：

- checkpoint 验证分别在读取语义根、读取 checkpoint head 后延迟返回。新 session 接管租约后，即使旧读成功返回完整结果也不能激活旧实例；原根和档案不变，新 session 仍可恢复原输入。与既有测试中 `load` 自身因旧租约抛错不同，这两例到达 barrier 的失效检查。
- 有效档案缺少 File 字节时拒绝恢复，并断言具体缺失材料错误，不能因无关异常通过。原 metadata、原文、文件名和时间保持完整；用同一个完整档案可以恢复，无额外存储写入。
- 缺少精确任务定义时，允许打开用于保留和审查的 Workspace，但执行恢复明确返回 `recovery-definition-missing`，不将任务消费或调用不存在的定义。保留并再次导出后，用正确版本恢复成功，只 lookup 一次、原服务执行仍只有一次。不能将“打开了恢复界面”误称为任务已恢复。
- 多行任务第二目标分别被删除、被同业务 key 的新身份替代、被撤销写权限。三者均不得部分写入第一行；完整结果和输入保留，显式消费再次拒绝，原状态和新身份数据不变。

基础的内存回调不可导出、任务定义版本不匹配已存在于 `checkpoint.test.ts` 和 `recovery-scan.test.ts`，本轮未复制这类单点断言。
