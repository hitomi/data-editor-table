# 完整工作流成本基线

当前证据来自 `src/kernel/workflow-measurement.test.ts` 的五个完整流程及同目录的 `workflow-cost-baseline.json`。测试使用生产 Workspace、准备/接纳、保存协调、恢复与checkpoint导出，后端和存储由独立 SourceFixture / RecoveryFixture 提供。运行时为 Node v24.19.0。

每个流程均执行：编辑接纳 → 冻结原coverage → 请求尚未执行时接纳后继输入 → 服务器规范化 → 精确回执与刷新 → 新租约重开pending后继 → 保存后继 → 再次重开 → 导出checkpoint。断言完整文档、隐藏字段、原始输入、原意图、两次请求的各自coverage和原冻结字节不变，服务端恰好执行两次写入。

## 可复现命令

```sh
KERNEL_WORKFLOW_REPORT=/tmp/kernel-workflow-measurement pnpm test src/kernel/workflow-measurement.test.ts
```

默认单元测试只运行正确性断言；指定该环境变量才写出每个场景的JSON测量文件。Node文件I/O在测试专用的 `tests/kernel/workflow-report.mjs`，不会给浏览器内核添加Node全局类型。运行时间只作为观察数据；30秒是测试执行超时，不是产品性能承诺。

## 本次保存的样本

单位为ms；逐次历史行的准备/接纳是所有动作的累计时间。batch是一份输入的一次批量动作，history则每次编辑都独立持久接纳，二者保证的持久边界数量不同。

| 场景 | 命令/动作数 | 准备累计 | 持久接纳累计 | 冻结至Source入口 | 重开pending | 存储写次数 | 最终record字节 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| batch | 32/1 | 2.41 | 22.02 | 28.55 | 3.28 | 20 | 43,028 |
| batch | 128/1 | 2.83 | 57.25 | 133.55 | 9.53 | 20 | 141,911 |
| batch | 512/1 | 11.40 | 183.46 | 356.31 | 43.95 | 20 | 541,655 |
| history | 32/32 | 20.21 | 167.61 | 32.19 | 3.94 | 51 | 63,089 |
| history | 128/128 | 342.46 | 2818.70 | 125.37 | 14.85 | 147 | 224,410 |

五个场景的前沿节点数分别等于原命令数：后继动作引用了原动作最后一个意图，所以比仅准备原动作时的N−1多一个。512命令batch的最终journal为345,925字节，checkpoint metadata为1,082,583字节。所有数值的完整阶段明细在JSON中。

## 证据的含义与限制

当前样本中，准备节点引用的成本小于持久接纳、冻结和保存协调成本；逐次接纳时累计成本明显增大。下一步应拆分生产存储的编码、摘要、记录写入和恢复读取，而不是继续只优化节点append次数。不能据此合并或省略本应独立确认的输入持久边界。

这不是IndexedDB浏览器测量，也没有真实网络或文件资源：RecoveryFixture自身还会复制、校验并留存每次完整写入供断言使用。因此这些时间不能直接归因于生产存储实现，亦不能用作设备延迟或渐近复杂度证明。单次样本受JIT、GC和运行负载影响；早先观察与最终记录存在波动，JSON保留的是最终完整单次运行，没有挑选最快结果。

本轮未修改生产代码。定向五个流程、全量69文件/1265单元、类型/边界/lint通过；此前生产树的387三浏览器、10语义变异及发布包门禁结果仍有效，本轮没有重复这些未受运行时代码变化影响的门禁。真实存储剖析、长历史/压缩及其余M0–M6验收继续开放，完整Goal未完成。
